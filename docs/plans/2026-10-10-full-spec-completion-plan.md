## 3. Общие архитектурные решения

### 3.1 ColorSquarePalette — единая палитра со случайной раскладкой (R50)
- `ColorSquarePalette.tsx` — единственный источник выбора цвета. Добавить props `randomize?: boolean` (default `true`): при каждом mount/shuffle-запросе порядок квадратов перемешивается (`Math.random`), выбор возвращает цвет.
- Все места выбора цвета переводятся на неё: готовка (запись), маршруты (маршрут), контракты (период), чат (контакт — с фильтром уже использованных), виртуальные карты/финансы.
- Для тестов: `data-testid="color-square-{index}"` и seed-режим (`deterministic` prop) в unit-тестах; E2E проверяет только факт перемешивания (два mount → порядок отличается хотя бы раз на N попыток — flake-free через 10 попыток).

### 3.2 Грамматика «страницы выбранных элементов» (R19, R20)
Общий компонент `SelectedElementsWorkspace` (вынести из текущих 6+ инлайн-реализаций):
- Шапка: **стрелка-назад в левом верхнем углу**, **«Сохранить» в правом верхнем углу**.
- Список выбранных элементов; клик → редактирование → возврат на страницу (состояние страницы сохраняется).
- Семантика: после «Сохранить» сохранённый элемент **исчезает** из списка выбранных; после «Назад» (стрелки) — **остаётся**. Выход из режима только когда список пуст (Сохранить) или по стрелке.
- Применить к: курьеры (отключение), заказы, контракты, клиенты, виртуальные карты, транзакции, low-админы, ингредиенты, записи готовки, маршруты, контакты чата.
- Тест-контракт: `tests/selected-elements-workspace.spec.ts` (unit на семантику исчез/остался + E2E на переходы).

### 3.3 Движок доступности (availability) — каскад и маркеры (R9–R14, R18)
- Таблица `ResourceAvailability` (override по дате) остаётся источником правды для отдельных дней. Добавляется слой **эффективного состояния периода контракта**:
  - `effectiveContractDay(contract, date)`: период ENABLED + нет override-отключения **этого или любого предыдущего дня внутри периода** (каскад вперёд) + день входит в `enabledWeekdays`.
  - Отключение дня внутри периода админом/universal-кнопкой пишет override на эту дату; каскад вычисляется при чтении (без массовой записи) — так «периоды длятся вечно, пока не сменят друг друга» не требует бесконечных строк.
- **Маркеры границ** (R12): при отрисовке календаря вычисляются виртуальные маркеры: перед первым включённым днём после отключённого периода рендерится «отключённый маркер-день», перед первым отключённым после включённого — «включённый маркер-день» (виртуальные, без записи в БД; визуально — дни-разделители). Функция `computePeriodBoundaryMarkers(period, overrides, window)` в `src/lib/contracts/` + unit-тесты.
- **Каскад заказов** (R18): при чтении заказов — заказ в отключённом (эффективно) дне считается отключённым (не попадает в список курьера, помечается DISABLED на UI). Включение отдельного заказа пишет ORDER-override на его дату (ENABLED) и CONTRACT-override на соседние даты (DISABLED: предыдущая и следующая в рамках периода). ORDER-ветка `resource-availability` уже существует — подключить чтение в `couriers/effective-assignment.ts` и surfaces курьера.
- **Жёлтая подсветка** (R9): в `ResourceCalendarPanel` активные дни периода в назначенные будни — `bg-amber-100` + жёлтая рамка; отключённые — красные; маркеры — по §3.3.
- **Линия курьера над периодом** (R13): маркер первого дня периода красится `getCourierColor(period.courierId)`; полоса рисуется над всей строкой-неделей периода (top-border периода), а не только inset слева; универсальное окно календаря получает markers как ContractsTab.

### 3.4 Режим временных веток (R26) — предлагаемая семантика (допущение)
Спецификация не определяет ветки детально («учитывают историю действий с контактами»). Принимаемая семантика (зафиксировать в ledger, пометить как допущение):
- «Временная ветка» = снимок текущего состояния страницы (ресурс, фильтр, выбор, режим), в котором пользователь может безопасно пробовать изменения; изменения не применяются, пока ветка не «применена».
- Вход: ключ + поиск → открывается панель веток: список активных веток сессии, «Создать ветку из текущего состояния», «Применить», «Отбросить».
- Ветка учитывает историю действий: в карточке ветки виден лог действий, совершённых внутри неё (ActionLog с `branchId`).
- Хранение: в памяти сессии (zustand/context) + sessionStorage; без изменений схемы БД. Если пользователь захочет персистентность — отдельный цикл.

## 7. Риски и допущения
1. **Временные ветки** — семантика в спецификации не определена; принятая (§3.4) помечена как допущение; при другом замысле пользователя — пересмотр без изменения остальных циклов.
2. **Полигон на карте** — рисование мышью требует E2E-хаков (координаты viewport); предусмотрены programmatic-хелперы и unit на point-in-polygon.
3. **ORS API** — нужен `OPENROUTESERVICE_API_KEY` (в .env.example есть); при отсутствии ключа линия маршрута деградирует до прямых сегментов (fallback), функционал не блокируется.
4. **Миграции** — additive только (`contractId`, возможно индексы); `defaultCourierId` не удаляется в первом проходе (перестаём писать, колонка остаётся).
5. **Каскад при чтении vs записи** — выбран расчёт при чтении (без массовых записей); риск производительности низкий (периоды ≤ 30 дней в горизонте), но при росте — кэшировать effective-состояние.
6. **Случайные цвета** — рандомизация может ломать визуальные регресс-тесты; все такие тесты — на факт перемешивания, не на конкретный порядок.
7. **Объём** — 12 циклов; спецификация требует «не останавливаться», поэтому циклы выполняются подряд без ожидания подтверждений, каждая сверка с pasted_content_3/4/5 фиксируется в ledger.
